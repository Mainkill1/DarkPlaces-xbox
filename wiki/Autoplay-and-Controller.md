# Automatic demo loop and controller operation

## Intended operation

The engine's Xbox attract profile starts without keyboard or controller input:

```
normal Host_Init -> first active frame -> xbox-benchmark.cfg
 -> validated playlist -> first demo -> next demo -> wrap to first
```

A freshly pressed controller button (including a trigger) stops playback and opens
the menu. The takeover press is consumed, so A cannot also confirm a menu choice.
Held buttons must be released before another action is accepted. Stick movement
and drift do not leave demo playback. Start from the menu deliberately restarts
the playlist; there is no timer that unexpectedly takes control back from a user.

The normal intended stress workload is **one complete-world route in one demo**.
A list of up to eight demos is also supported. Replaying a demo may reload its
world; seamless rendering at a loop boundary is not established by this change.

## Current gate and branch

`port/nexuiz-autoplay-controller` is stacked on the Nexuiz preparation branch, not
merged into the pending foundation smoke. It adds real engine call sites,
controller sampling, and package-generated configuration. It does not add the
missing Xbox system/filesystem/renderer link set. The original two-source smoke
XBE therefore still cannot load a game or play a demo.

On a future engine-linked build with `DP_PLATFORM_XBOX`, the profile is automatic.
For the existing desktop SDL reference engine, explicitly pass `-xboxbenchmark`.
Without that option, ordinary desktop startup and input selection remain unchanged.
Do not combine this profile with `-demo`, `-benchmark`, `-capturedemo`, or `-listen`;
those are separate one-shot/interactive startup modes.

## Package-time configuration: no guessed demo filenames

`tools/xbox/nexuiz_prepare.py stage` automatically creates `xbox-benchmark.cfg`
whenever the explicit asset selection includes `.dem` files. It includes joystick
settings, Nexuiz action bindings, and the actual selected demo paths. By default
those paths are sorted; repeated `--demo PATH` options select an explicit order.
The generator rejects missing selections, duplicates, over-eight playlists, unsafe
paths, and a command longer than the small-memory input-line capacity.

Use `--require-autoplay` for a benchmark package so a selection with no demo cannot
silently succeed as an autoplay-ready package:

```sh
python3 tools/xbox/nexuiz_prepare.py stage \
  --data-dir /work/Nexuiz/data \
  --selection /work/nexuiz-selection.json \
  --output /work/nexuiz-autoplay-pack \
  --require-autoplay
```

The output contains `data/xboxprep.pk3` and `manifest.json`. Configuration bytes,
source generator identity, selected playlist, package hashes, and generated byte
counts are recorded. Existing source content cannot silently replace the generated
configuration. The tool still does not infer dependency closure or validate that a
demo's maps, CSQC, textures, and materials are Xbox-compatible. No actual Nexuiz
content is bundled with this branch. Keep `xbox_ready: false` until the later gates
are genuinely tested.

For desktop reference testing, put the prepared pack on an otherwise complete,
verified Nexuiz content search path and launch the normal SDL executable with
`-nexuiz -basedir /work/prepared-content-root -xboxbenchmark`. The root's `data/`
folder must contain all required content, not just the demo or generated config.
The config is executed after normal startup configuration, so recorded gameplay
settings should be deliberately pinned rather than inherited from a personal profile.

## Controls

These are **logical SDL GameController actions**, translated to the existing
DarkPlaces `X360_*` key names. The names do not imply an Xbox 360 requirement.
The pinned nxdk SDL maps the Original Xbox's White/Black buttons to the left/right
shoulder slots; the adapter uses those semantic slots rather than raw indices.

| Context | Control | Result |
|---|---|---|
| Automatic playback | Any fresh mapped button or trigger | Stop loop, consume the press, open menu |
| Automatic playback | Either stick | Ignored; no camera or takeover effect |
| Menu | D-pad or left stick | Navigate |
| Menu | A / B / Back | Confirm / back / back |
| Menu after stop/error | Start | Restart the playlist from demo one |
| Manual gameplay | Left stick / right stick | Move/strafe / look |
| Manual gameplay | Right trigger / left trigger | Primary / alternate attack |
| Manual gameplay | A / B | Jump / crouch |
| Manual gameplay | White / Black | Previous / next weapon |
| Manual gameplay | X / Y | Drop weapon / previous selected weapon |
| Manual gameplay | Left click / right click | Hook / zoom |
| Manual gameplay | Start or Back | Open menu |
| Desktop playback | Escape | Stop and open menu; consume repeats and release |

Nexuiz bindings refer to its game aliases (`+attack2`, `+crouch`, `+hook`, `+zoom`,
`weapprev`, `weapnext`, `weaplast`, and `dropweapon`). These require the real game's
config/game logic; they are not newly implemented game actions.

Stick endpoints are normalized without exceeding +/-1, Y is converted to the
engine's positive-up convention, and the generated movement/look deadzones are
0.266. SDL-mapped triggers use 0..1, not the raw Xbox axis range. Trigger button
edges use 0.20 engage / 0.10 release hysteresis. Menu stick navigation requires
0.55 deflection. Rumble, chatpads and arbitrary unmapped joystick layouts are not
claimed. Standard mapped controllers are supported; unmapped devices are skipped.

The adapter chooses the first recognized controller without a Start prompt and
retains its instance identity. A controller added later does not steal ownership.
Unplugging produces neutral input and releases previous actions; the next recognized
pad is selected automatically. Reconnect-held buttons need a neutral observation
before becoming actions. No controller is required to start or continue autoplay.
This is a one-player controller policy, not simultaneous multiplayer input.

## Engine boundaries and failure behavior

- `host.c`: boot hook after Host_Init and frame hook after command execution.
- `cl_attract.c`: bounded playlist, input takeover, menu/resume and signon timeout.
- `cl_demo.c` / `cl_parse.c`: actual file opening, EOF and protocol-disconnect hooks.
- `xbox/attract_policy.c`: allocation-free lifecycle, input edge gate, bounded header parser.
- `xbox/controller_sdl.c`: real SDL controller initialization, ownership and polling.
- `vid_sdl.c` / `vid_shared.c`: sample translation and correct menu/game key contexts.
- `keys.c`: Escape consumption for desktop reference operation.

The future `vid_xbox.c` must initialize/poll/shut down the same controller adapter,
feed samples through `CL_Attract_Controller`, and then call `VID_ApplyJoyState` once
per engine input update. Do not invent a parallel mapping or send duplicate key
events. The current desktop SDL backend already makes those calls; the native
Xbox renderer/system backend is still separate work.

Missing files, malformed headers, truncated records, invalid message sizes, early
EOF before signon, or signon taking longer than `xbox_demo_loadtimeout` (default
60 seconds, constrained to 1..600) stop the loop with `XBOX_AUTOPLAY_FAILED`.
They do not repeatedly retry broken content. A later active frame opens the menu
once, after disconnection. Manual map/connect/disconnect cancels automatic replay.
A signon timeout is not a general host/GPU hang watchdog and cannot interrupt a
blocked renderer call.

`xbox_demo_status` reports state, current index, and completed loops.
`xbox_demo_stop` leaves autoplay; `xbox_demo_start` revalidates and restarts it.
Input changes occur only in the opted-in profile (or Xbox build). The corrected
bounded demo header/record parsing and legacy list bounds check also protect normal
desktop playback from the same malformed input cases.

## Tests and native controller check

Host tests compile the real policy and adapter source. The engine-adapter test uses
service doubles for filesystem/demo/menu boundaries, not a loaded game. SDL tests
use an actual SDL virtual joystick with the Original Xbox raw layout and verify
mapping, axis signs, triggers, removal and reconnection. Content tests prove
configuration generation and deterministic packaging with synthetic fixtures only.

```sh
# Host requires compiler and SDL2 development files; CI makes SDL tests mandatory.
DP_REQUIRE_SDL_TESTS=1 python3 -m unittest discover -s tests -p 'test_*.py' -v

# Optional separate on-console input diagnostic, NOT the game or primary smoke.
make -C xbox/inputcheck NXDK_DIR=/work/nxdk V=1
```

The input diagnostic links the same controller adapter against the pinned nxdk SDL
and produces `xbox/inputcheck/disc/default.xbe` plus `controller-check.iso`. It
prints raw/logical input and exercises takeover edges. It explicitly says that it
is input-only: it does not call Host_Init, load maps, or render a demo. Keep its
artifacts separate from the original smoke and from any claimed engine benchmark.

Acceptance still requires desktop playback against real content, then Xbox engine
integration and real hardware/xemu tests of first boot, no-input repeated playback,
held buttons, deliberate exit, menu navigation, analog gameplay and unplug/replug.
These remain under issues #23, #25, #27 and #28; compilation does not close them.
